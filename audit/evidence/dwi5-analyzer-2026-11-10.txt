Reading
-------
- Cases 1 and 2 resolve to a single top-level function / static method element.
  A generator can name a static target; the function has no captured
  environment.
- Case 5 does not resolve to one target. The initializer shows two candidates,
  but the analyzer does not track which branch executes. A generator would have
  to reject it unless it also proved the value set, which is whole-program
  data-flow analysis that a package does not have.
- Cases 3, 4 and 6 expose the closure AST and its captures. For case 4 the
  probe reports `connection: Connection (UNSUPPORTED)`; a generator can reject
  it deterministically. Case 3 and 6 have a serializable capture, but the
  analyzer does not lift the body or prove that the body is compilable outside
  its lexical scope.
- The instance tear-off control resolves the method but not a static target:
  the receiver is a runtime value.

Limits
------
- Resolution only; no generated worker, no compilation, no execution.
- The `_serializable` map in the probe is the DWI v0.3 wire-type whitelist, not
  a general Dart type judgement.
- A resolved element does not guarantee that the function survives dart2js
  tree shaking; that requires a generated static reference (probe 3).
- The stub's `Object?` parameter accepts any argument. A real API signature
  would constrain some of these forms before the body is analyzed.
