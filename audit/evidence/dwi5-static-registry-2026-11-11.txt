What the prototype does
-----------------------
1. Writes a task library with @DwiTask() addOne, twice, identity and busyPrimes.
2. Runs discovery (discoverTasks) and emits a test-only generated caller registry:
     final Map<Function, String> dwiCallerRegistry = <Function, String>{
       tasks0.addOne: "addOne",
       tasks0.twice: "twice",
       tasks0.identity: "identity",
       tasks0.busyPrimes: "busyPrimes",
     };
   The keys are static Dart references, not names.
3. The host chooses addOne or twice at runtime, looks the tear-off up in the
   map, and calls the existing Dwi.run<int>(taskName, 21). No function value is
   sent to the worker.
4. It also resolves both entries directly (addOne -> 22, twice -> 42), and looks
   up an unregistered function (null, not executed).
5. It runs busyPrimes, which delays 200 ms inside the worker and counts primes
   <= 100000 while a 10 ms main-thread timer counts ticks.
6. It runs identity, whose token is created inside the worker program, and reads
   Dwi.capabilities() for the observed worker backend.

Assertions
----------
- selectedName == mappedTask.
- mappedResult == 22 for addOne and 42 for twice.
- mappedAddOne == 22 and mappedTwice == 42 (both registry entries).
- unregisteredMapped == null (the registry is closed over registered tasks).
- busyPrimes == 9592 (pi(100000)).
- ticks > 0 (main thread kept running while the worker computed).
- workerToken != hostToken (the token was created in a separate program).
- backend == worker.
- workerBackend == dart2js for the JS worker, dart2wasm for the Wasm worker.
- workerCount >= 1; protocolVersion == 2.

What this establishes
---------------------
- A generated caller registry can map registered top-level/static tear-offs to
  task names by identity and execute them end to end from a dart2js host in a
  real JS worker and a real Wasm worker.
- The main thread keeps ticking while the worker computes, and the worker's
  token differs from the host's.
- The observed worker backend matches the requested one.
- Both registered entries work; an unregistered function has no mapping.

Limits
------
- Prototype only: the registry generator lives in the test and is not part of
  the public builder or API. A consumer cannot call Dwi.run(fn) today.
- Registered static tear-offs only. Closures and arbitrary inline bodies still
  need a compiler/build transformation that lifts the body and captures.
- An unregistered or dynamically created function value has no task ID; the
  prototype returns null rather than executing it or falling back.
- The host imports the task library to build the map, so those functions are
  also compiled into the host bundle. The cost was not measured.
- Chrome only; Safari, Firefox and Edge were not run.
- Native VM end-to-end execution of this mapping was not tested.
- A dart2wasm host + Wasm worker end-to-end run was not performed; only the
  dart2wasm host identity map and a dart2js host + dart2wasm worker run are
  measured.
- No Flutter build-hook or fresh-build test; this is a plain Dart web fixture.
- No public API decision, no compatibility-level raise.

Reading for the matrix
----------------------
Cases 1, 2 and the registered-static subset of 5 now pass end to end on a
dart2js host + JS worker and a dart2js host + Wasm worker, through the
prototype registry. The dart2wasm host identity map passes separately
(run_static_identity_wasm.sh), but a dart2wasm host + Wasm worker end-to-end run
was not performed. This is still not a public function API, so DWI-5 itself is
not raised. Cases 3 and 6 remain blocked by tooling; case 4 remains rejected by
design.
