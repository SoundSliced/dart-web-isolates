Acceptance checks under the prototype
  Task execution: a probe app whose task returns 424242 + seed reported
  `RESULT:424243` in document.title and the server logged
  `GET /dwi/worker.dart.js 200` — the task ran in the worker.
  Root and subpath: with `--base-href=/sub/app/`, the page fetched
  `GET /sub/app/dwi/worker.dart.js 200` and still reported RESULT:424243.
  Regeneration: editing the task and then a helper file changed the packaged
  worker (c2079… → 207943… → f035e9…) and rebuilt successfully.
  Cache: an unchanged rebuild logged `Skipping target: build_hooks` and
  `Skipping target: dart2js`.
  Wasm worker target: with `dwi.yaml: target: wasm`, a rebuild published
  build/web/dwi/gen-<hash>/{worker.mjs,worker.wasm} and worker.boot.mjs.
  Missing worker asset (fails): removing build/web/dwi/worker.dart.js makes the
  page request it (404) and throw an uncaught
  `TypeError: Cannot read properties of undefined (reading 'gq')` from
  main.dart.js's Worker error callback. The caller's future never settles and no
  typed DWI error reaches the app. This is independent of build ordering and is
  a separate defect.
  Caveat found: creating `dwi.yaml` after a first build does not invalidate the
  hook (the hook only declares dwi.yaml as a dependency when it already exists),
  so the target change needs a source edit or a clean build to take effect.

Conclusion
  The gate does not pass on the shipped package for any first ordinary
  `flutter build web` (js, wasm, debug). `flutter run -d chrome` (debug) passes
  because Flutter's resident web runner orders hooks before its compile; that is
  one mode, not the gate. A one-line build-graph change makes every mode pass in
  the prototype. Until Flutter ships an ordering/output contract for build hooks,
  the supported first-build workflow stays `dart run dwi_builder:dwi build`
  once, before the first Flutter build.
