Source findings (installed SDK, read-only inspection)
  1. `Dart2WebTarget.dependencies` is
     `[WebEntrypointTarget(), GenerateLocalizationsTarget()]`
     (flutter_tools/lib/src/build_system/targets/web.dart:143);
     `Dart2JSTarget extends Dart2WebTarget` (web.dart:166). `build_hooks` is not
     among those dependencies, which is why the compiler can start before the
     hook writes `lib/dwi_tasks.g.dart`.
  2. `BuildHooks(platform: HookPlatform.web)` is only a dependency of
     `LinkHooks` (native_assets.dart:140), and `LinkHooks` itself depends on the
     compile targets (`extraDependencies: compileTargets`, web.dart:601-604).
     Hooks therefore influence linking, after compilation, never source
     resolution during compilation.
  3. `BuildHooks` exposes exactly one output, `{BUILD_DIR}/build_hooks_result.json`
     (native_assets.dart:119-125); a build hook has no supported way to declare a
     Dart source file as an input that `dart2js` must wait for.

Candidates evaluated
  | Candidate                                            | Outcome |
  | commit generated proxies                             | rejected: generated output is gitignored and would be stale; contradicts ADR-008 determinism rules |
  | declare proxies as hook output/asset                 | not supported: hook outputs feed LinkHooks after compilation (source findings 2-3) |
  | app-root hook/build.dart                             | not run by Flutter (ADR-009 measurement) |
  | dev_dependencies hook                                | not run by Flutter (ADR-009 measurement) |
  | app uses `Dwi.run` and imports no generated proxy    | works end to end, verified above; loses typed proxy sugar |
  | CLI/dwi-build-first workflow                         | works; already the documented fallback |

Additional defect found and fixed during this probe
  `dart compile js -o <temp>` also writes `<temp>.deps` and `<temp>.map`. Those
  leaked next to the published worker and were copied into `build/web/dwi/`
  (observed: worker.dart.js.<pid>-<micros>.tmp.deps, .tmp.map, 13,174 B and
  116,821 B). `compileWorker` now deletes the companion files after publication
  and after a failed publication, and the build test no longer accepts a
  `.tmp`-anywhere name as "clean". Re-measured: `web/dwi/` and
  `build/web/dwi/` contain only `worker.dart.js`.

Verdict
  The ordering limitation is a Flutter build-graph property, not a DWI defect,
  and no supported SDK mechanism removes it. The zero-manual-build gate for the
  typed-proxy workflow stays OPEN. The supported initial workflow remains one
  `dart run dwi_builder:dwi build` (or `dwi build --flutter-build`) before the
  first Flutter build; afterwards ordinary Flutter commands keep the worker
  fresh. A fresh project that calls `Dwi.run` and imports no generated proxy
  does build and run in a worker on one command, as measured above.
  NOT PROBED in this session: `flutter run -d chrome` (debug/hot reload),
  flutter build web --wasm, and worker replacement while a page is live.
